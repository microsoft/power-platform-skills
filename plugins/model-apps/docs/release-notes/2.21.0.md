# model-apps 2.21.0 — release notes

The full account of what changed for someone upgrading from 2.20.6. The [CHANGELOG](../../CHANGELOG.md) entry is the short
index of the same release.

## Summary

2.21.0 lets an App Spec carry more of an app, and keeps the items a spec declares in step with it when you rebuild. Views,
charts, web resources, form layouts and Global Standard dashboards can be **declared** (`reconcile: "declared"`): the build
then keeps the fields the spec states and leaves every other setting alone. Business rules and process flows can be created
and adopted as complete workflows. The spec also gains portable schema fields, configuration items, an app theme (Preview),
Quick Find search columns, exact Main forms and declared pins. Generative pages gain content and navigation drafts, and
read-only tools show what a build would do before it does it.

The bundled SDK is updated (commit `0eef55f8c2d0`); the `pcf` plugin carries the same bundle.

## Upgrading from 2.20.6

- **Every new feature is opt-in.** A spec that uses none of them sends the same requests as 2.20.6, apart from the extra
  reads listed under *Changed* and the default-view handling under *Fixed*.
- **Set `"minimumPluginVersion": "2.21.0"`** in a spec that uses a feature that needs it, so an older plugin refuses the spec
  instead of ignoring the field. Each feature's schema section says whether it needs it
  ([capability floors](../../references/app-spec-schema.md)).
- **Keep the managed binding store with the workspace.** Declared forms, dashboards, rules and process flows keep a local
  store in the build workspace (normally `.maker-workspace/managed-bindings.<hash>.json`). It holds ids, proof and baseline
  hashes, pending change and publication state, and the supported declarations. It holds no credentials and is not
  telemetry. Stable view and chart groups keep baselines rather than their original declarations.
- Printed `--authorize` approvals are quoted for the shell.

## Added

### Declared items

`reconcile: "declared"` on a view, chart, web resource, form, Global Standard dashboard, business rule or process flow. The
fields the spec states follow it; settings it does not state are preserved. Business rules and process flows are **create and
adopt only**: the build does not edit the body or state of an existing one. It creates them as Draft, proves them, then
activates them with a conditional write.

- **Adopting an existing item** needs its typed approval, `--authorize adopt:<family>:<key>` (for example
  `adopt:dashboard:<key>`).
- **`--verify`** checks declared view columns, filters and sort, and web-resource content. Bound forms, dashboards, rules and
  process flows are checked with fresh identity reads and the proofs the build recorded. Charts are checked for presence,
  not content.
- **Download.** `download-model-app.js --include-managed --managed-manifest <store file>` writes back the form, dashboard,
  rule and process-flow declarations the store proves, and only those. Views, charts and field-security profiles are not
  reconstructed, and this is not a general export of managed web resources.
- **Removing a declaration deletes nothing.** For managed forms, dashboards, rules and process flows, a removed declaration
  whose item a maker deleted in Maker can be retired once fresh exact-id reads prove it absent (form rows must be absent in
  both layers). Re-declaring a retired key creates a new identity. An unresolved publication can prevent retirement. An
  unconfirmed form or dashboard retirement stops further service writes in that invocation; for rules and process flows the
  affected table or name stays fenced. The next invocation reads afresh. Views, charts and web resources do not have this
  retirement path.
- **Local copies.** A local copy of a managed item that differs from the server's stops the build
  (`workspace-copy-unsent-edits`). Where the stop prints an `overwrite:` key it may be used; otherwise recovery is manual.
- **Dashboards.** Each tile a build creates is sent with its declared caption in every provisioned language, so the build's
  proof compares exactly what it sent. A caption in another language that the platform drops is accepted; every caption
  present must match, and a caption the build did not send is never accepted. A build that cannot read the provisioned
  languages stops before it writes the dashboard. A later rebuild judges a tile only on the parts the spec declares (its view
  or chart, and its caption in the build's language).
- **Publishing.** Without `--publish`, a declared form's table and a declared dashboard are still published; the flag decides
  only when. Reads that lag behind a publish are retried for up to about 45 seconds per scope, plus the time of the requests.

Each family has its own section in the
[advanced schema reference](../../references/app-spec-schema-advanced.md): *views[].reconcile · charts[].reconcile ·
entities[].quickFind*, *forms[].reconcile*, *dashboards[].reconcile*, *businessRules[].reconcile* and
*businessProcessFlows[].reconcile*.

### Stable create ids

`createIdentity: "stable-v1"`, for **new apps only**: declared views and charts reuse their create ids when a build is
retried. Other kinds keep their own create paths. A change that is not yet proved withholds its table's publish. An
unresolved publication needs the documented observation, or the printed `--authorize publication-risk:<scope>/<dispatch>`
decision, which a run accepts only at its start, records, and then stops; the next run publishes. See *createIdentity* in the
advanced schema reference.

### Portable schema fields

Explicit Choice option values (`{ "value", "label" }`), Date and Time behaviour (`dateTimeBehavior`), column field security
(`isSecured`) with `fieldSecurityProfiles[]`, and table flags (`searchEnabled`, `changeTrackingEnabled`,
`duplicateDetectionEnabled`). A destructive schema edit asks for a named `--authorize <key>`, one key per change. Downloads
always write option values and `isSecured`; `--include-capabilities` also writes Date and Time behaviours, table flags and the
app theme. See *columns[].dateTimeBehavior · option values · table flags* in the advanced schema reference.

### Configuration items

Environment variables (secrets included), connection references, Custom APIs, duplicate-detection rules and
`solution.version`. Per-environment values come from a `--deployment-settings` file, never from the spec. See
*Configuration items* in the [schema reference](../../references/app-spec-schema.md).

### App theme (Preview)

`app.theme` brands the app header and logo. Downloads need `--include-capabilities`. `--verify` checks the saved and resolved
API state, not what a browser paints.

### Quick Find, exact Main forms and declared pins

`entities[].quickFind.findColumns` sets a table's Quick Find search columns. `app.mainFormsOnUpdate: "exact"` takes the
table's other Main forms out of the app's membership on an update (no form is deleted; on an existing app it needs
`--allow-destructive`). `app.pinDeclaredArtifacts` adds the spec's declared forms, views, charts and dashboards to the app
explicitly. A lost component-add answer is checked afterwards, and a recoverable missing pin is repaired once; otherwise the
build reports itself incomplete.

### Pages

Content and navigation drafts, pages leases, and `prepare-compiler-refresh`. A host that retries one identical page request
can use `genpage-upload.js --turn-id <guid> --app-dir <folder>`; the id must be chosen before the first send and reused from
that folder. Do not pass `--turn-id` for an ordinary create or edit. See the
[genpage skill](../../skills/genpage/SKILL.md).

### Read-only tools and data repair

- `--dry-run --preview-push` shows, per artifact, whether a push would create, update or change nothing, and what would stop
  it. It reads only.
- `--inspect-components`, with `--verify`, checks command buttons by their recorded rows.
- `solutions.js inspect` lists what a solution holds, and `plan-app-promotion.js` plans whether an app can move to another
  environment. Neither writes.
- **`data-fix.js` writes rows.** It plans a change first and applies it only with the plan's approval.

These are described in the [app-builder skill](../../skills/app-builder/SKILL.md).

## Changed

- **Builds read slightly more.** Column reads add `IsSecured`; every name match is read; Date and Time behaviours are read
  before a table gains columns; every form is read, page by page, before a page is deleted or an app is torn down.
- **Teardown keeps** pages that a form embeds, configuration items and declared field-security profiles, and names them.
  Downloads do not write configuration items.
- **Page edits** halt on a declared connection or Custom API that cannot be used, and wait while an app publication is
  unsettled.
- **Duplicate-detection rules** and their conditions resolve their solution component types from the service.

## Fixed

- **Default views.** A default view whose workspace copy names no table is never edited or sent. Clean or identity-only
  copies, compared with the SDK's stored server snapshot, are refreshed on later attempts or runs, including runs that did
  not create the table. Other unsent changes are preserved and halt the build with keep/discard guidance.
- **A table that was just created.** The service can answer a default-view save with metadata-cache errors for a table it has
  only just created. A build retries that save only for a table the invocation itself created, across the whole build's
  attempts; the default budget is four attempts (three retries), possibly with no view save. The 2.20.6 first-build failures
  that were observed recovered on a rerun.
- **Emptying a declared web resource** finishes, confirmed by reading the row back.
- **A refused app-access unlink** fails the build. **A process-flow delete** answered "no active transaction" is sent again.
  **A process step with an unknown outcome** is never run twice.
- **A dashboard create whose content cannot be proved** stops naming the dashboard's id. Delete it only when the message says
  this build created it; otherwise inspect it in Maker first, as it may be someone else's work.

## Known limitations

- **Saved form and dashboard layers.** Dataverse does not version a form's or dashboard's saved layer, so a Maker edit made at
  the instant of a build's write cannot be detected (the SDK re-reads the saved layer just before it writes).
- **Existing workflows.** Existing business rules and process flows are not edited by the build.
- **Publish checks** skip a caption in a language the published read does not return, and some saved labels. An adopted form
  whose saved and published layers differ in a base-language caption may need the risk approval again on each build, after you
  check the published form in Maker.
- **Publication risk.** `--authorize publication-risk:<scope>/<dispatch>` is accepted only at the start of a run, which records
  it and stops without service writes; rerun to publish. Re-declare a removed dashboard to publish it.
- **Managed downloads** omit a declared process flow that has `securityRoles` (a download writes no personas, and the warning
  names them: copy the flow and its personas from the spec it was built from), and a declared form whose event-handler library
  is not downloaded (listed in `managedForms.stale`). Views, charts, field-security profiles and configuration items are not
  downloaded, and charts are verified for presence only.
- **Local-copy recovery** uses the printed `overwrite:` keys where they exist, and is otherwise manual (see the
  [advanced schema reference](../../references/app-spec-schema-advanced.md)). `--allow-destructive` covers exact Main forms on
  an existing app, emptied web resources and Quick Find, and removed view columns.
- **Metadata lag.** A first build right after it creates a table can still stop on the service's metadata-cache lag (for
  example when it looks views up by name, or confirms a new process flow's identity): wait for metadata to propagate, then
  rerun; more than one rerun may be needed. The same class of lag was also observed with 2.20.6.
- **Duplicate rules** that are saved but not published must be published. **Unprovisioned languages** fail the build after the
  solution is created.
- **Lost-create retries.** A whole-build retry after a lost create answer can duplicate configuration rows. A table discovered
  only after its create answers "already exists" can need another build to repair a declared Date and Time behaviour before
  columns are added.
- **Not supported:** keyed command bars (refused), `forms[].genPages`, and inspecting a component by caption alone (it fails).
