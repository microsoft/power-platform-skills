# Mobile App Screen Design

Own build-ready visual direction, per-screen layouts, control selection, responsive behavior, interaction states, and accessibility specifications. Do not implement production React Native screens or components. Navigation is supporting context, not the focus of this stage.

Read [stage-contract.md](../create-mobile-app/references/stage-contract.md), [template-contract.md](../create-mobile-app/references/template-contract.md), and [ux-quality.md](../create-mobile-app/references/ux-quality.md).

## Procedure

1. Require a complete Plan stage and reuse its compatibility snapshot. Inspect only Plan-stage changed files plus the existing routes, components, Tamagui tokens, and root boundaries directly consumed by Screen Design; do not rescan auth/provider/template files unless the handoff reports a relevant change or targeted verification detects drift.
2. When visual references are supplied, analyze them before designing. Extract transferable qualities rather than copying the source: hierarchy, palette proportions, typography contrast, whitespace, density, image treatment, section transitions, control geometry, persistent actions, navigation chrome, and overall emotional tone. Record `Adopt`, `Adapt`, and `Avoid` decisions in the plan. For references like a premium commerce screen, useful qualities may include a disciplined dark/light palette, editorial headline hierarchy, one strong photographic anchor, compact uppercase utility labels, crisp product imagery, restrained borders, generous content spacing, and an integrated sticky action area. Apply those qualities to the app's own domain and brand.
3. Establish one clear product-specific visual direction from the requirements, reference analysis, and existing brand, and record it as a one-sentence concept that later stages must preserve. Define implementable semantic token names and values for light/dark color roles, typography families/weights/sizes/line heights, spacing/density, radii, borders, elevation, imagery, icon family/size roles, surface hierarchy, and one or two restrained visual motifs. Define palette proportions, not only color swatches, so one dominant foundation, one contrasting surface, and sparse accents create intentional hierarchy. Give the default/home tab one restrained token-driven gradient on its signature identity or status surface with verified contrast, brand-aligned colors, and a shared `GradientSurface` contract tied to the home Screen ID. Record the exact token contract in Markdown for Stage 3/4 to implement through the existing Tamagui and `PowerAppsProvider` boundaries. Prefer a decisive codebase-aligned direction over asking the user to choose a generic style; ask only when competing directions would materially change the product.
4. For every planned screen, define its purpose, user job, information hierarchy, focal point, realistic content, primary and secondary actions, business rules, and cited requirement/acceptance-scenario IDs under `## Screen Design Specifications` in `.stages/mobile-app-plan.md`. Preserve Stage 1's four or five tab roots and descendant graph exactly, then generate `### Screen Navigation Graph` as the build-facing restatement of those same route IDs, tab branches, presentation modes, and forward/back/cancel/deep-link edges; resolve ambiguity but do not add scope. Add one shared bottom-navigation contract covering tab order, labels/icons, default tab, selected/unselected/focus/pressed/badge states, safe-area ownership, long/localized labels, keyboard behavior, and compact/expanded treatment; each screen records its owning tab, visible back/cancel behavior, platform-native edge-swipe back behavior, and any conflict with horizontal content or row gestures. Do not define personas or hard-coded role variants.
5. Design complete screen compositions rather than collections of cards or isolated components. Give each primary screen one memorable compositional idea tied to the task: for example an image-led context panel, a compact status band, an editorial summary, a scan-friendly product/record row, a master-detail workspace, or a persistent total/action dock. The default/home dashboard must lead with the approved token-driven gradient hero, then show its four data-backed summaries in a compact responsive grid (`2x2` at compact width and four columns when space permits), followed by a prioritized actionable list and one supporting context region; specify hierarchy, freshness, destinations, and loading/empty/error behavior for every region. Use full-width surface changes, whitespace, alignment, scale, imagery, and typography to create hierarchy before adding containers. Make the primary action unmistakable and keep persistent actions integrated with safe areas and content rather than floating arbitrarily. Specify content regions, visual rhythm, scan order, density, progressive disclosure, persistent versus scrolling areas, and how long or localized content changes the composition. For dense operational screens, define aligned scan lanes, compact but readable rows, pinned identifiers/status/actions, grouping and separators, truncation/expansion rules, and what moves into disclosure or overflow; density must increase decision speed without shrinking body text, touch targets, focus indicators, or error/help content.
6. Reject generic output even when it is functionally complete. Redesign any screen dominated by equal-sized cards, repeated icon-in-circle tiles, excessive pills, weak gray-on-white hierarchy, arbitrary gradients, uniform spacing with no rhythm, placeholder copy, decorative metrics, or every section enclosed in a rounded rectangle. Cards are for repeated records or truly framed tools; use dividers, bands, rows, typography, imagery, and whitespace for page structure. Do not turn an operational screen into a marketing landing page merely to make it visually dramatic.
7. Select a rich but purposeful control set for each screen. Evaluate and use the controls that improve the task: text and numeric fields, multiline input, search with suggestions, switches, checkboxes, radio groups, segmented controls, tabs, chips, date/time pickers, selects, sliders or steppers, progress, status badges, rich record rows, data tables on expanded layouts, charts/data visualization, media, upload/capture controls, contextual menus, tooltips, popovers, dialogs, alert dialogs, bottom sheets, carousels, swipe actions with visible alternatives, pull-to-refresh, floating/contextual actions, and AI assistance only when required. Distinguish `data-card` from compact `record-row`, `content-carousel` from form `range-slider`, and workflow `step-indicator` from task `progress-state`; compose search filtering from `search-field` plus `adaptive-sheet`, and reuse `form-field`, `segmented-control`, and `empty-state` rather than specifying duplicates. On the account screen, show only sourced profile fields, use an accessible system/light/dark single-choice control, and make sign-out a clearly labeled destructive action with confirmation plus loading/error/no-real-account states. Do not add controls for novelty. Record the chosen scaffold ID or framework primitive, intent, states, and phone/tablet adaptation.
8. Evaluate modern interaction patterns separately for every relevant screen and select only patterns that materially improve its task:
	- bottom sheets for focused choices, filters, previews, or short forms, with safe areas, keyboard avoidance, drag/close affordances, focus management, and dialog/popover adaptation on larger layouts;
	- rich record cards or rows with clear hierarchy, status, a small contextual action set, unambiguous press targets, and accessible action names;
	- horizontal carousels only for genuinely browsable related content, with a visible continuation cue, preserved position, touch/keyboard support, and no auto-advance;
	- smart search with debounced suggestions, recent/popular options when useful, highlighted matches, result-count announcements, keyboard controls, and complete loading/empty/error states;
	- pull-to-refresh only for refreshable list/detail data, with controlled refreshing, preserved context, success/error feedback, and a visible accessible refresh alternative;
	- recommendations with a clear rationale, dismiss/refine controls, and a useful non-personalized fallback;
	- swipe gestures only for efficient secondary actions, always paired with a visible alternative and undo for destructive outcomes;
	- floating or context-aware quick actions only for high-priority actions derived from the current item, selection, backend outcome, or workflow state; keep them reachable and clear of keyboards, content, and system controls;
	- AI assistant panels only when conversational or generative help solves a defined task; distinguish generated content and provide loading, failure, dismiss, retry, and user-control behavior;
	- determinate progress when measurable and indeterminate progress otherwise, always paired with meaningful text or an accessible value and never fabricated precision;
	- short, interruptible micro-animations that explain state or spatial change and provide reduced-motion behavior.
	Record selected and rejected patterns with rationale. Repeated selected patterns become reusable component candidates. Use established project primitives and do not add a dependency for an interaction that existing Tamagui, Expo, or React Native capabilities can express clearly.
9. Create a state matrix for every screen. Give every required state a stable state ID and cite the acceptance-scenario and mock-scenario IDs that make it reachable. For each of loading/skeleton, content, empty/action, recoverable error/retry, offline/unavailable, backend permission denied, validation, submitting, optimistic/rollback where justified, success, disabled, selected, pressed, focus-visible, overlay open, and relevant record-status states, mark `required` or `not applicable` with a reason. For every required state, specify realistic content, hierarchy and control changes, available actions, feedback/announcement, focus behavior, responsive layout impact, recovery or next action, and the matching HTML anchor when represented. Skeletons preserve final geometry; persistent failures use inline banners; transient confirmations use the configured toast channel. The UI consumes backend outcomes and never predicts authorization from account labels.
10. Generate content-driven compact, medium, and expanded layouts covering compact phone, compact-height/keyboard-open, wide phone or foldable, tablet, landscape/split-screen, and web when targeted. Record one named responsive viewport contract with exact width/height or container constraints and the corresponding live Tamagui media keys; every screen cites those names and specifies what reflows, appears, disappears, or becomes persistent at each boundary. Include hinge/occlusion avoidance where a foldable layout is relevant and touch, keyboard, mouse/trackpad, hover, and focus behavior for supported web input modes. Use Tamagui stacks, tokens, media/responsive props, flex, aspect ratios, and min/max constraints rather than device-specific offsets. Define safe areas, system bars, keyboard behavior, orientation, scrolling, virtualized collections, readable maximum widths, and deliberate one-column to multi-column or master-detail reflow without merely scaling the phone design.
11. Define reusable versus screen-specific component composition with preferred Tamagui primitives, typed props/events/slots/variants, stable component IDs, token dependencies, and all required usage Screen IDs. Reconcile every screen's controls, states, repeated behavior, and semantic/platform boundaries against the existing component inventory and scaffold manifest; map each need to an appropriate shared component or framework primitive, or record why it remains screen-specific, with no need silently omitted and no irrelevant component selected. In the authoritative `### Component Map`, classify each entry as `shared component` or `framework primitive`: Stage 3 implements only shared components; framework-owned composition such as Expo Router `Tabs` remains a Stage 4 implementation requirement and must not receive a custom CP wrapper. Every shared component must serve repeated behavior or a stable semantic/accessibility/platform boundary and name at least one screen that must consume it; omit speculative components. Consolidate the map under `## Screen Design Specifications` in `.stages/mobile-app-plan.md` and cite it in the Stage 2 artifact/handoff; repeated behavioral patterns become reusable components while screen-level hierarchy, section geometry, and visual rhythm remain outside the shared library. Separately define one mandatory screen-shell contract and a `### Screen Shell And Inset Ownership Matrix` with one row per Screen ID and relevant default/keyboard/overlay context. Record the shell mode, native-header visibility, scroll versus virtualized-list owner, keyboard avoidance, maximum width/gutters, fixed footer/tab spacing, and the single top/bottom/left/right inset owner. Produce one coherent cross-platform design. Record native-safe behavior only where implementation must respect host-platform behavior; do not create separate iOS and Android visual designs.
12. Make WCAG 2.2 AA readiness part of each component and layout contract without claiming conformance before testing: logical screen-reader and keyboard order, accurate names/roles/values/states, visible unobscured focus, 44x44 targets where practical, text/non-text contrast, non-color status cues, dynamic type/font scaling, increased-contrast behavior, locale-aware reading order, reduced motion, single-pointer gesture alternatives, status/live-region announcement timing, and focus management for overlays and failed forms. Add a per-screen interaction/semantics matrix covering each control's `A11Y-*` ID, interaction class, persistent visual affordance, web and native name/role/value/state, keyboard behavior, and default/hover/pressed/focus-visible/disabled/selected/busy appearance; separately identify main/heading/list/group/live-region structure and actionable versus static row variants. Render materially distinct states in the HTML checkpoint, including a static and actionable row where used. Specify input purpose, keyboard type, `autoComplete`/platform autofill semantics, paste/password-manager support, one-time-code behavior, and error association for every relevant field. Authentication must avoid memory/puzzle barriers where possible and define accessible alternatives for biometric, timeout, reauthentication, or cognitive checks. Test realistic long/localized text and increased text size for clipping, overlap, and loss of function.
13. Specify purposeful imagery/media with stable asset IDs, source or asset strategy, Expo module, rights/license and attribution requirements, aspect ratio, bounded dimensions, crop/focal behavior, loading/error/offline fallback, caching, permissions, and accessibility descriptions. Map every media ID to its Screen IDs and representative content. Use bundled or user-provided assets when imagery is brand-critical or must work offline. When temporary Unsplash photography is appropriate, require a stable image URL, photographer/Unsplash credit surface, and replacement note; dynamic search requires the official API with credentials outside source control. Give meaningful images contextual alternatives, suppress decorative images, and define captions/transcripts/audio descriptions for introduced audio or video. Do not use unrelated stock imagery to fill space. When imagery is central, make it a meaningful compositional anchor with an intentional crop and legible foreground treatment rather than a small decorative thumbnail.
14. Define a few short, meaningful transitions, state animations, and haptic/press feedback using configured Tamagui/Reanimated capabilities. Motion must explain hierarchy, progress, or state change, remain interruptible, preserve task speed, and respect reduced-motion preferences.
15. Keep navigation specification focused: preserve every planned route and edge, specify when the persistent bottom bar and back/cancel control are visible, and confirm each descendant returns within its owning tab while direct deep links have the Stage 1 fallback. Do not invent additional routes or turn full navigation simulation into the primary prototype requirement.
16. Generate `.stages/02-screen-design.html` as a lightweight, self-contained rendered checkpoint at compact mobile width only for the primary screens, signature compositions, and materially distinct required states. Use semantic HTML, embedded CSS/JavaScript, real domain copy, realistic data, and the defined visual system; do not require a server or external package. Include enough state and interaction controls to validate each distinct visual pattern without duplicating equivalent states across every screen. Navigation may be a simple screen selector and need not simulate the full route flow.
17. Keep `.stages/mobile-app-plan.md` and `.stages/02-screen-design.md` authoritative for behavior, data, controls, accessibility, responsive rules, component map, shell matrix, and every required state. Label represented screen/component/state IDs in the HTML exactly as cited by the Markdown matrices and define reusable visual tokens. Use HTML only to demonstrate visual hierarchy, composition, responsive transformations, and representative interaction states; never treat HTML/CSS as React Native implementation source. Annotate web-only approximations such as safe areas, native controls, gestures, font metrics, and motion.
18. Perform at least two rendered visual-refinement passes at compact mobile width. First inspect each primary screen at thumbnail scale and in grayscale: the focal point, section hierarchy, primary action, and reading order must remain obvious. Then inspect at actual compact width with realistic long content and required representative states. Compare supplied references by transferable qualities, not pixel similarity. Revise weak hierarchy, excessive containers, timid imagery, monotonous spacing, awkward crops, generic controls, and detached sticky elements before declaring the design complete.
19. Review every required state in the authoritative specification and render each materially distinct compact-width visual pattern. Capture compact-width screenshots or equivalent rendered evidence. Check hierarchy, scan-efficient density, alignment, content quality, control affordance, text/non-text contrast, visible focus, reading order, dynamic/localized text, autofill/error semantics, compact-height keyboard/safe-area handling, reduced motion, overflow, and overlap. Include representative light, dark, increased-contrast, and large-text evidence when required. Review medium and expanded behavior in the Markdown specifications; later stages validate those form factors in web viewports. Record native-only behavior as unverified unless the user supplies wrapped-device evidence; never launch a simulator or dev client.
20. Review specification, Screen Navigation Graph, bottom-navigation contract, reference translation, visual quality, exact token contract, per-screen hierarchy, interaction/semantics matrices, control/form-operation bindings, component map, screen-shell/inset matrix, state-to-scenario/HTML traceability, media contracts, interaction patterns, accessibility, and named responsive layouts directly against this stage's completion criteria. Block completion when a downstream implementer would still need to invent a route edge, back fallback, component API, field mapping, breakpoint, inset owner, required state, interaction affordance/semantics, or visual-system value. Validate the HTML checkpoint by rendering and inspecting it, not by parsing its source with a one-off script. Do not run dependency-dependent commands. Exclude `src/generated/` from direct inspection. Stage 3 runs the first dependency gate. Provide `.stages/02-screen-design.html` as the primary review target.

Do not create domain services, mock fixtures, production components, or feature screens. Native, connector, and Dataverse behavior is represented only as planned screen states and boundaries. Do not let route or platform-variant documentation displace visual design, responsive composition, rich controls, or accessibility work.
