# Mobile App Plan

Own workspace classification, requirements discovery, environment intent, the requirements-level screen graph, and the complete implementation plan. Do not implement app features or mutate external systems.

Read [stage-contract.md](../create-mobile-app/references/stage-contract.md), [template-contract.md](../create-mobile-app/references/template-contract.md), [data-architecture.md](../create-mobile-app/references/data-architecture.md), [ux-quality.md](../create-mobile-app/references/ux-quality.md), and [app-plan-template.md](../create-mobile-app/assets/app-plan-template.md).

## Procedure

1. Locate the template root, read existing plan/state, and build the compatibility snapshot from `template-contract.md`. Classify it as fresh, in-progress, existing custom app, or incompatible.
2. Verify package scripts/versions, `PowerAppsProvider`, auth/protected routes, customization markers, `expo.extra.powerappsNative`, Metro/Babel invariants, and optional Power Apps/offline configuration. Exclude `src/generated/`; record deviations without repairing them.
3. Ask one open workflow question when the request is thin, then at most two compact batches for unresolved facts required to define behavior, records/actions, exception paths, platforms, native needs, connections, Dataverse, offline use, brand, accessibility, environment, repeated-task density, input methods, supported locales/content formats, authentication input needs, media/assets and rights, and mock scenarios. Record whether the workflow needs image-led data cards, search filters, bottom sheets, swipe actions, carousels, multi-step progress, or empty/error recovery; do not require a pattern without a user need. Infer sensible codebase-aligned defaults and discover environment values later when supported tooling can do so.
4. Do not ask for personas, roles, stage omissions, or client-side authorization rules. Model supported operations and backend allowed/denied outcomes; the backend remains authoritative.
5. Separate confirmed requirements, assumptions, constraints, deferred ideas, and acceptance scenarios. Give every requirement and acceptance scenario a stable ID and a concrete Given/When/Then outcome so later screen states and mock fixtures can cite it. Treat template auth, provider, CLI generation, and verification behavior as constraints unless a supported change is requested.
6. Create `## Requirements Screen Graph` in `.stages/mobile-app-plan.md`: define exactly four or five distinct primary destination screens in one authenticated bottom-tab shell, designate the default/home tab, and originate relevant detail, create, edit, and focused workflow routes from their owning tab nodes. Plan the default/home tab as an at-a-glance dashboard with a data-backed token-driven gradient status/identity hero, exactly four useful summary metrics, a prioritized actionable list, supporting time-sensitive context, data freshness, and navigation from each actionable summary; reject decorative or duplicated metrics. Include a reachable account screen for sourced profile information, system/light/dark theme preference, and sign-out with loading/error/no-real-account outcomes; profile fields must come from an approved repository or host API, never fabricated token/account assumptions. Include every route, entry point, labeled transition, modal/sheet, success/cancel path, and meaningful error, empty, unavailable, allowed, and denied outcome. Label each navigation edge as tab switch, push, replace, back, dismiss, or deep link; every non-root screen must define its owning tab, expected back/cancel destination, deterministic direct-entry fallback, and native edge-swipe back policy with the same outcome as its visible back control. Record which screens support pull-to-refresh, its repository operation and loading/error outcome, and any row swipe actions plus visible alternatives. Add one inventory row per route with stable Screen ID, typed route/search parameters, navigation role/owning tab, entry and exit paths, primary action, denial behavior, and expected information density. Trace every requirement and acceptance-scenario ID to a screen or named non-UI/system behavior; every screen must cite at least one requirement and scenario.
7. Record selected and rejected Expo/platform opportunities with user value and rationale, plus high-level native, Power Apps connection, Dataverse, generated-interface, and offline intent.
8. Define the technical architecture around the existing `PowerAppsProvider`, Expo Router auth shell, protected `app/(app)/` route group, Tamagui config, and customer-owned `app/`/non-generated `src/` boundaries. Preserve route IDs and template auth routes.
9. Resolve each screen's data needs into intent-named repository operations with explicit typed query/mutation inputs, outputs, ordering/paging behavior, and domain-error outcomes. For every form or command, bind the planned field names, types, required/optional rules, and validation constraints to the matching operation input. Also define native wrapper boundaries, Power Apps connection adapter operations, Dataverse mappings, and backend permission-denied outcomes.
10. Define domain models, repository interfaces, and deterministic realistic mock scenarios outside `src/generated/`. Give each mock scenario a stable ID, trigger/operation input, fixture characteristics, expected result or domain error, and acceptance-scenario IDs exercised. Include normal, long-content, dense-list, empty/filter-zero, loading, recoverable-error, validation, denied, and mutation-success cases when relevant. Screens depend on repositories, never host configuration or generated services directly.
11. Create `## Expo And Tamagui Experience` from the live package inventory. For every selected capability record the user need, installed package/API, architecture boundary, platform behavior, fallback, permission/config needs, and evidence required; record rejected capabilities as `Not used` with a reason.
12. Define the Tamagui theme/token, deliberate typography, spacing/density, semantic color, component, responsive/input-mode, overlay, motion, imagery/media-rights, localization, and accessibility strategy. Inventory by Screen ID every repeated behavior and stable semantic, accessibility, layout, or platform boundary that Stage 2 must evaluate as a shared-component need, without defining component APIs here. Target WCAG 2.2 AA criteria in design and implementation contracts without claiming conformance before applicable automated and manual testing. Give each interactive or intentionally static surface and dynamic outcome an `A11Y-*` acceptance ID mapped to its Screen/requirement/scenario IDs; classify it as navigation, command, toggle, single selection, disclosure, or static content, and require a visible affordance plus accurate name, role, value/state, keyboard/touch behavior, focus/error behavior, and web/native announcement outcome. Prefer marked extensions to replacement configuration.
	Record each shared-component candidate with its Screen IDs, common anatomy/behavior, stable semantic/accessibility/layout/platform boundary, and expected variation; leave API design and the promote/reject decision to Stage 2.
	Read the component-scaffold manifest metadata and record each candidate's preferred scaffold ID or `custom`, fit rationale, known gaps, dependency hints, and intended depth role (`flat`, `raised`, `floating`, or `modal`). Treat these as Stage 2 inputs, not final API or promotion decisions.
13. Inventory native capabilities against installed dependencies and Expo config plugins. Mark unsupported capabilities rather than planning unshipped modules.
14. Define required non-Dataverse Power Apps connections and actions, including ownership, request/response fields, generated service location, mock-backed adapter contract, and domain error translation.
15. Define Dataverse entities, fields, choices, relationships, ownership, reuse decisions, dependency tiers, and generated service consumers. Schema mutation remains subject to its later approval gate.
16. Add a CLI generation manifest for every connection and table data source, including supported command family, expected generated types, and consuming adapter contract. Never plan handwritten generated interfaces or raw HTTP.
17. Reconcile technical feasibility with the screen graph. Ask only when a material product or integration choice cannot be resolved from the request and persisted facts.
18. Verify the graph has four or five reachable tab roots, no orphan screens or dead ends, and a valid forward, back/cancel, and direct-entry path for every descendant. Verify every screen maps to requirement and acceptance-scenario IDs, typed route parameters, repository operations, deterministic mock scenarios, and purposeful framework capabilities. Verify every form field maps to an operation input and input-purpose/autofill semantics, every required exception path has a reachable scenario, locale-sensitive values have a formatting rule, authentication inputs support accessible completion, and every external media asset has a rights/attribution plan. Identify root-config edits and prefer none.
19. Split implementation into 10-12 minute waves in the required stage order. Include every stage and do not ask which stages to skip.
20. Create/update `.stages/mobile-app-plan.md`, `.stages/mobile-app-state.md`, and `.stages/01-plan.md`; mark Plan complete only when compatibility, graph completeness, stable IDs, requirement/scenario and `A11Y-*` interaction traceability, typed route and repository coverage, form-operation alignment, mock-state coverage, architecture, and integration coverage pass with no required decision unresolved.
21. Review the package manifest, template anchors, plan structure, route inventory, architecture, and traceability directly. Do not run dependency-dependent commands or generate a Markdown parser. Exclude `src/generated/`. Provide the home route, screen graph, and plan as review targets.

Do not define final per-screen layouts or component props, and do not write app feature code in this stage. Stage 2 owns the build-ready screen specifications.
