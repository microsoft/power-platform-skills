# Mobile App Builder

Own domain contracts, mock data, feature screens, navigation, and complete end-to-end workflows built on the existing code and approved component library.

Read [stage-contract.md](../create-mobile-app/references/stage-contract.md), [template-contract.md](../create-mobile-app/references/template-contract.md), [data-architecture.md](../create-mobile-app/references/data-architecture.md), [ux-quality.md](../create-mobile-app/references/ux-quality.md), and [implementation-patterns.md](./references/implementation-patterns.md).

## Depth Consumption

Require and consume each Component Map depth role exactly: keep structural sections and ordinary rows `flat`, use `raised` cards selectively, reserve `floating` for menus, popovers, and detached action docks, and reserve `modal` for overlay content. Do not add screen-local `shadow*` styles or elevate containers merely for decoration.

At the complete-app visual gate, verify the `flat`/`raised`/`floating`/`modal` hierarchy in light, dark, and increased-contrast modes at compact and expanded widths. Reject clipped shadows, missing border fallbacks, accidental elevation on page sections, and overlays that do not read above underlying content.

## Procedure

1. Require complete authoritative Screen Design specifications, their `Visual Token Contract`, `Responsive Viewport Contract`, `Component Map`, `Screen Shell And Inset Ownership Matrix`, per-screen state/control/form and input-purpose bindings, localization and authentication accessibility contracts, media rights/alternatives, WCAG 2.2 AA readiness evidence, rendered `.stages/02-screen-design.html` checkpoint, and a complete Component Library handoff. Before coding, trace every Screen ID through requirement/acceptance IDs, typed route parameters, repository operations, mock scenarios, state/HTML IDs, and implemented reusable components; return `BLOCKED` to Stage 1 or 2 at the owning gap rather than inventing behavior. Extract a visual acceptance checklist for each screen from the Markdown and HTML: signature composition, scan-efficient density, palette proportions, edge-to-edge bands, content gutters, typography hierarchy, icon roles, imagery, persistent actions, safe-area edges, compact-height behavior, and compact/expanded transformations. Verify every planned shared component has a real file, customer-app handoff entry, named value/type exports, required production Screen IDs, typed props/events/slots, required theme variants, representative state evidence, passing import-boundary check, and resolvable import; verify the target barrel exports no `ComponentGallery`, demonstration component, or export without a required production Screen ID, and verify framework-primitive entries have no redundant Stage 3 wrapper. Require one shared screen-shell implementation compatible with the per-screen ownership matrix; return `BLOCKED` to Stage 3 if it is absent or incompatible. Injected scaffold files are now customer-owned; consume only the selective target barrel without recopying or importing skill assets. Return `BLOCKED` to Stage 2 for a missing/incomplete rendered checkpoint, ambiguous implementation contract, or materially weak visual direction.
2. Set data mode to `mock` and create domain models, intent-focused repository interfaces, deterministic fixtures, in-memory adapters, and one composition point under `src/`. The app-owned resource/repository provider must run beneath the host `QueryClientProvider`, obtain its exact instance with `useQueryClient()`, expose that `queryClient` with the repositories, pass it to every adapter factory that uses React Query, and memoize the composed context value by `queryClient`; never create or omit the client because a mock factory does not yet use it.
3. Build on the existing root `PowerAppsProvider`, Tamagui config, auth routes, protected `app/(app)/` layout, Metro/Babel configuration, tokens, and shared components. Implement the approved four or five primary destinations with Expo Router `Tabs` in one authenticated bottom-navigation shell, using a nested stack for each tab's descendant routes so the tab bar remains present across authenticated feature screens; auth/callback routes and true modal overlays remain outside it. Preserve the planned tab order, default tab, route IDs, owning-tab relationships, and deep-link/back fallbacks; do not expose descendant routes as extra tabs. Preserve the installed native stack's type-verified platform edge-swipe back behavior, keep a visible back control with the same destination, and disable the gesture only for a documented interaction conflict. Verify the installed host contract and preserve its inputs for auth, Power Platform configuration, generated schema map, Tamagui, theme tokens, optional offline profile, and supported callbacks. `PowerAppsProvider` already owns Gesture Handler, `ThemeProvider`, `TamaguiProvider`, portal/toast, `QueryClientProvider`, auth, and Power Apps host context. Never recreate any of them or instantiate a second query client; repositories and screens consume the host query client. Add only contexts not owned by the host, such as safe-area, app repository composition, or an approved feature-specific provider, once and in dependency order. Compose shared component slots and typed variants before forking a component for one screen. Add authenticated feature routes under `app/(app)/`; replacing starter `home.tsx` is allowed, but bypassing or duplicating template providers/auth is not.
4. Implement at most three related screens per wave from the Markdown behavior, state, accessibility, visual, and responsive contracts. Consume Stage 3 components only through their type-checked handoff APIs. For one-off Tamagui primitives, treat the installed package/config types as authoritative: use only compiler-accepted props/shorthands, registered theme names, token-safe values, and verified compound members. Do not copy unverified long-form style props from HTML/React Native, widen dynamic token maps to `string`, invent state themes, or assume members such as `Sheet.Title`; derive dynamic value types from the receiving component prop and model state with typed variants when needed. Components enhance repeated behavior, accessibility, and state; they do not dictate or replace screen composition. Build each page hierarchy deliberately with Tamagui primitives and a small number of reusable contracts. The default/home production route must preserve the approved gradient hero, four-card responsive summary grid, prioritized actionable list, supporting context, freshness, and region states; a hero plus undifferentiated rows or fewer than four useful summaries is incomplete. Do not assemble a screen as a uniform padded stack of default components, wrap every section in a shared component/card, or force distinct layouts through one generic component API. Preserve the approved full-width bands, whitespace, alignment, scale, gutters, rows, imagery, and persistent actions as native responsive composition.
5. Use the HTML only as visual evidence of hierarchy, proportions, color distribution, density, and responsive intent. Never translate DOM structure, CSS dimensions, class names, absolute positioning, or browser layout mechanics into React Native. For every represented screen, record what native composition adopts, adapts, and intentionally differs; unexplained visual flattening is a failure even when functionality and types pass. Screens never consume fixtures or integration services directly.
6. Route every feature screen through exactly one safe-area owner. Prefer the shared screen shell with explicit top/bottom edge ownership; account separately for native stack headers, tab bars, keyboard avoidance, scrolling lists, and fixed action docks. Never rely on ordinary `paddingTop`, a hidden Expo Router header, or a bottom-only footer inset to protect the iOS status bar, Dynamic Island/notch, home indicator, or Android system bars. Do not nest full-edge `SafeAreaView`s. Verify the first focusable/header content and final action remain inside measured insets at compact width and increased text size.
7. Complete every approved workflow with rich functional behavior: bottom-tab switching with retained branch history, descendant push/back/cancel flows, direct deep links with deterministic fallback, virtualized scan-friendly lists, forms, search/filtering, media presentation, refresh/retry, destructive confirmation, draft preservation, feedback, and all specified states. Implement planned pull-to-refresh with the owning `FlatList`/`ScrollView` refresh API, controlled repository refresh state, feedback, and a visible refresh alternative. Consume approved `data-card`, `search-field`/`adaptive-sheet`, `swipeable-row`, `content-carousel`, `segmented-control`, `step-indicator`, and `empty-state` contracts through the Stage 3 barrel; preserve visible row-action alternatives and destructive undo, and do not substitute redundant screen-local wrappers. Use replace only for terminal transitions that must not return to the submitted/invalid screen; never create back loops or orphan routes.
	For search filters, use the Stage 3 `SearchField` popover menu for a short option set and `AdaptiveSheet` for multi-field or explanatory filtering. Cards with approved icon or action affordances must consume the typed Stage 3 slots instead of rebuilding local card chrome.
8. Make mock repositories return deterministic allowed and permission-denied outcomes for protected operations. Use these to validate backend-authoritative access handling without personas, role switches, or client-side authorization rules.
9. Keep app/domain code in customer-owned `app/` and outside `src/generated/`. Never import `power.config.json`, generated services, or host configuration into screens. Never read, create, patch, or manually edit files under `src/generated/`.
10. Configure the app-specific design through the existing `PowerAppsProvider`: pass approved light/dark `ThemeTokens` through its `theme`/`darkTheme` props, enable `followSystemTheme`, and extend the supplied `tamaguiConfig` only inside its customization boundary. Implement one app-owned theme-mode context beneath that host provider: own the `system | light | dark` preference, initialize it from approved persistence when planned, resolve `system` with `useColorScheme()`, and wrap descendants in Tamagui's existing `Theme` component with the resolved named `light` or `dark` theme. Bind the Account control to that context preference and expose one action that persists it, updates the app context, and uses the installed host's verified `useThemeControl()` contract to reset the host theme for `system` or apply the matching approved host tokens for `light`/`dark`; if any step fails, restore the previous mode in both layers and show a visible error. This app context is not another theme provider: never mount another `ThemeProvider`, `TamaguiProvider`, `QueryClientProvider`, or query client. Implement the account screen from its planned profile repository; call only the installed host's verified `useAuth().signOut`/`hasRealAccount` contract and let the protected layout return successful sign-out to login. Define semantic color roles, surface hierarchy, spacing/radius/elevation choices, and named typography roles for display, heading, title, body, label, and caption with deliberate family, weight, size, line height, and scaling behavior. Reuse installed fonts or load approved app fonts through Expo Font before rendering dependent routes, provide a deterministic fallback, and consume typography through Tamagui font/text tokens rather than repeated screen literals. A default untouched config does not satisfy an approved product-specific palette or typography contract. Verify manual light, manual dark, and system mode under simulated light/dark OS schemes by checking both host surfaces and Tamagui token-driven components.
11. Use installed capabilities deliberately: Tamagui themes/tokens/responsive variants and animation; Expo Image/Asset/Font for visual assets; React Hook Form with Zod for forms; React Query through the host-owned query client for repository server-state; and Material Community Icons as the single app icon family. Use icons in navigation, scan/search/filter, status, disclosure, and familiar compact actions where the Screen Design specifies them; pair unfamiliar/primary/destructive/mode-changing actions with labels, and give icon-only controls an accessibility label and 44-point target. Text such as `Back`, `Close`, or glyph substitutes does not satisfy a specified familiar icon control. Do not use Unicode glyphs, emoji, hand-drawn SVGs, or mixed icon families when the installed family provides the semantic icon. Use installed Tamagui primitives directly for one-off presentation when the Component Library intentionally omitted a trivial wrapper. Permissioned hardware/file workflows remain behind Stage 5 wrappers.
12. Add immediate action feedback with inline state, configured toast/banner, progress, or navigation outcome. Use meaningful motion and preserve reduced-motion behavior; avoid generic animation on every interaction.
13. After each wave, run `npm run type-check` and update a component-consumption ledger mapping every Stage 3 handoff entry to all required Screen IDs and its actual production render path, direct or through a selected component; demonstration-only files and unused imports do not count and must be removed. Reconcile the completed ledger one-for-one with the Stage 3 handoff: every entry must render on every cited screen, every approved screen component must be present, and the target barrel must contain no surplus export; otherwise return to Stage 2/3 to correct the map, implementation, and obsolete export before continuing. Add an interaction ledger mapping each planned `A11Y-*` ID to its production element, interaction class, visible affordance, web/native name-role-value-state contract, and acceptance scenario. A required component or accessibility contract missing from any planned screen is a failed wave. Do not silently substitute a primitive or another component. Also perform a source-level composition audit against that wave's visual checklist, including safe-area owner, edge-to-edge sections, theme tokens, typography roles, icon roles, compact/expanded rules, and proof that the resource/repository context exposes the same host query client returned by `useQueryClient()`. Do not run `npm run web`, `npm run dev`, any `bundle:*`/`build:*` script, or another complete-app build while screens, workflows, provider composition, theme, typography, or icon integration remain unfinished.
14. After every approved screen and workflow is assembled, run the first complete-app gate: `npm run type-check`, then `npm run bundle:web` when available and the relevant existing test. Start `npm run web` to capture rendered evidence. Never run `bundle:ios`, `bundle:android`, an Expo native launch command, an iOS/Android simulator, or a dev client. Verify the root still uses the host-owned provider stack with no duplicate theme, Tamagui, query, portal/toast, gesture, auth, or host providers. Exercise all four or five tabs, every graph edge, descendant back/cancel behavior, direct deep links, browser back, default-tab entry, and tab-history restoration; confirm the persistent bottom bar has no duplicate destinations, preserves each branch, and does not obscure content or keyboard/fixed actions. Validate in the web renderer at least one iPhone-like compact viewport with simulated top notch/Dynamic Island and bottom home-indicator insets, one compact-height keyboard-open case, one increased-text compact viewport, and one wide/tablet viewport. Exercise required light, dark, increased-contrast, reduced-motion, keyboard, pointer/hover/focus, autofill/error, and representative long/plural-content variants. For every route and required state, inspect the accessibility tree and rendered pixels: require zero console errors/overlays, no unnamed or false interactive elements, accurate names/roles/values/states and progress values, one main landmark and screen heading, valid list/group/live-region structure, visible keyboard focus, distinguishable actionable/static and enabled/disabled/selected states, and no tab/footer/keyboard obstruction. Statically reconcile the corresponding native `accessibilityRole`, `accessibilityState`, `accessibilityValue`, labels/hints, announcements, and focus behavior against the same ledger, marking native runtime behavior unverified rather than launching a native target. Inspect every route and representative loading/empty/error state for clipping, overlap, horizontal overflow, broken scrolling, unsafe content, misplaced fixed actions, obscured focus, and text truncation. Compare compact screenshots side by side with `.stages/02-screen-design.html` for composition, hierarchy, palette proportions, typography contrast, icon coverage, scan-efficient density, bottom-navigation fidelity, and action placement; validate wide/tablet layouts against Markdown. Fix material divergence before completion.
15. Web-rendered visual evidence is a non-waivable App Builder completion gate and the only runtime target App Builder may try. If web cannot render because of a host dependency or other prerequisite, return `BLOCKED` with type-check evidence, the failed web command, and the exact missing runtime prerequisite. Never fall back to iOS/Android, a simulator, a dev client, or another native target; never return `DONE`, `complete with exception`, or claim visual/safe-area quality from source inspection alone.
16. After the complete mock app passes its own gates, enable temporary mock-review auth mode. If `auth.config.json` still contains the template's empty `msal.clientId` and `msal.tenantId`, replace both with the non-secret all-zero UUID placeholder `00000000-0000-0000-0000-000000000000`; never overwrite non-empty registration values. Bypass both template auth gates so `/` redirects directly to the planned default tab and the authenticated tab shell renders without consulting `useAuth`. Keep `PowerAppsProvider`, `/login`, and `/oauth-callback` intact. Mark each source change `MOCK_PREVIEW_AUTH_BYPASS` so Stage 8 can find and remove it; do not spread bypass checks into feature screens. Parse `auth.config.json`, run type-check, and recheck the default tab in the existing web renderer after this change.
17. Record the per-screen visual checklist and reconciliation, final component-consumption ledger with no unused Stage 3 production exports, final `A11Y-*` interaction ledger, safe-area ownership map, rendered viewport and accessibility-tree evidence, verified host inputs/provider ownership, app-owned contexts, app theme and typography roles, icon family, validation evidence, route inventory, acceptance scenarios, whether auth placeholders were written, the exact bypassed files, and the pre-preview auth state as `empty` or `configured` without recording identifier values in `.stages/04-app-builder.md` and the handoff. Keep the stage `in-progress` and continue automatically while screens or scenarios remain. Once the complete mock app and temporary review mode pass, return `DONE` with the web URL and one concrete workflow for the user to try. The orchestrator must wait for that review before Stage 5.

The final Stage 4 audit must remove any `ComponentGallery.tsx`, gallery route/export, demonstration component, or other runtime file with no required production Screen ID.

Do not begin native, connector, or Dataverse work. The accepted mock app is the behavioral baseline every later integration must preserve.
