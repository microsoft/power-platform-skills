You are an expert in Power Platform solution packaging. The user has a Power
Pages site being migrated from SDM to EDM. A customization scan identified
custom columns on `adx_*` metadata tables that need to be moved into new
custom tables (per Microsoft's migration guidance — `adx_*` tables become
`powerpagecomponent` in EDM, so custom columns can't stay where they are).

The correct fix is to deliver a Dataverse solution package containing:
- One new custom table per affected `adx_*` table
- Each custom column moved to the corresponding new table
- A lookup column on each new table pointing to `powerpagecomponent` (so each
  new-table row is associated with its EDM component)

The user will import this solution into their environment and run a separate
data-migration step (covered at the end of this prompt).

## Your task

1. **Ask the user for their publisher prefix** (e.g., `contoso`, `acme`).
   This prefix is applied to all new table and column names. If they have an
   existing publisher in Dataverse, use it; otherwise help them pick one.

2. **Ask the user for the solution unique name** (e.g.,
   `<prefix>_PowerPagesEdmMigration`). This is the solution package name.

3. **Confirm the plan** with the user BEFORE building anything. Show the
   list of new tables and the columns/lookups each contains. Wait for
   approval.

4. **Initialize a new solution project:**

       pac solution init --publisher-name "<Publisher Display Name>" `
                         --publisher-prefix "<prefix>" `
                         --outputDirectory "./edm-migration-solution"

5. **For each grouping in the findings, create:**

   a. **A new custom table.** Naming: `<prefix>_<original-suffix>` (e.g.,
      `adx_webpage` → `contoso_webpage`). Conventions:
      - Display name: title-cased original suffix (e.g., "Webpage")
      - Primary name column: `<prefix>_name`, string, MaxLength 100

   b. **Each custom column from the finding** added to the new table.
      Use the SAME column logical name as the original (just on the new
      table — `contoso_redirecturl` stays `contoso_redirecturl`, not
      renamed).

      For column data types, infer from the column logical name (heuristic
      only — confirm with user when ambiguous):
      - Ends in `name`, contains `text|description|title|code|url|mimetype`:
        String, MaxLength 100
      - Starts with `is`, `has`, contains `enabled|compressed`: TwoOption
      - Contains `count|number` (and not an id): Integer
      - Ends in `id` and refers to a Dataverse entity: Lookup (ask user for
        the target entity)
      - Contains `date|time`: DateTime
      - Ambiguous: ASK the user

   c. **A lookup column** on the new table pointing to `powerpagecomponent`:
      - Logical name: `<prefix>_powerpagecomponentid`
      - Display name: "Power Pages Component"
      - Required: Yes (each row belongs to exactly one component)
      - On-delete behavior: ASK the user (Cascade cleans up extension rows
        when the component is deleted; Remove Link sets to null and leaves
        orphan rows. Default suggestion: Cascade for tighter coupling.)

6. **Show the user the solution structure** before packing. Show the
   directory tree and the entity XML for at least one new table.

7. **Pack the solution:**

       pac solution pack --zipfile "./edm-migration-solution.zip" `
                         --folder "./edm-migration-solution" `
                         --packagetype Unmanaged

   Default to Unmanaged so the user can inspect/modify after import. If the
   user plans to deploy to a production environment, ASK whether they want
   Managed instead (cleaner uninstall, prevents post-import editing).

8. **Document the import + data migration steps** (print, do NOT run):

   a. Import the solution:

          pac solution import --path "./edm-migration-solution.zip"

   b. After import, migrate row data from the old `adx_*` tables into the
      new custom tables. For each finding:
      - Read rows from the source `adx_*` table
      - For each row, find the corresponding `powerpagecomponent` row
        (joined by primary key — `powerpagecomponent` rows preserve the
        original adx_* row ID in EDM)
      - Create a row in the new custom table with:
        - The lookup column set to the matching `powerpagecomponent`
        - The custom column values copied verbatim

      Provide TWO sample data-migration approaches:

      **Approach 1 — Power Automate flow (low volumes, < 1000 rows):**

      Skeleton:
        Trigger: Manual / Recurrence
        Step 1: List rows from <adx_source_table> via Dataverse connector
        Step 2: For each row → Create a new row in <new_custom_table> with
                <prefix>_powerpagecomponentid = item().<primary_key> and
                <custom_columns> copied verbatim

      **Approach 2 — C# console app (higher volumes, batched):**

      Skeleton:

          using Microsoft.Xrm.Sdk;
          using Microsoft.Xrm.Sdk.Messages;
          using Microsoft.Xrm.Sdk.Query;
          // ... auth setup omitted ...

          var sourceQuery = new QueryExpression("adx_<source>") {
              ColumnSet = new ColumnSet("<custom_column1>", "<custom_column2>", "<source>id")
          };
          var sourceRows = service.RetrieveMultiple(sourceQuery);

          var batch = new ExecuteMultipleRequest {
              Requests = new OrganizationRequestCollection(),
              Settings = new ExecuteMultipleSettings { ContinueOnError = false, ReturnResponses = false }
          };

          foreach (var src in sourceRows.Entities) {
              var newRow = new Entity("<prefix>_<target>");
              newRow["<prefix>_powerpagecomponentid"] = new EntityReference(
                  "powerpagecomponent", src.Id);
              newRow["<custom_column1>"] = src["<custom_column1>"];
              // ... copy remaining custom columns ...
              batch.Requests.Add(new CreateRequest { Target = newRow });

              if (batch.Requests.Count == 1000) {
                  service.Execute(batch);
                  batch.Requests.Clear();
              }
          }
          if (batch.Requests.Count > 0) service.Execute(batch);

      Adapt the placeholders to the user's actual table/column names.

   c. After data migration, the user must:
      - Update any Liquid/FetchXML references to the old adx_* custom
        columns to instead query the new custom table via its lookup.
        (The SDM-to-EDM skill's FetchXML rewriter handles entity-level
        changes; custom-column references need this manual update.)
      - Then run the actual SDM-to-EDM migration via PAC CLI (a separate
        step in the migration skill, not in this remediation prompt).
